Capabilities & pass-through

Capabilities control high-impact actions such as restarting Home Assistant, controlling locks, writing automations, and reading logs. Start with a persona, then change individual capabilities only when needed.

How the modes work

Every capability holds one of three modes. Reading a mode in any code path goes through a single helper, so the pass-through interaction is always consistent.

deny

The operation is refused. This is the default for the riskier tiers.

allow

The operation runs, subject to the permission tree and MESA.

confirm

The operation is held as a pending approval until a human approves it in the panel. This is honored even under pass-through and across both network MCP and in-process agent surfaces.

confirm is only meaningful for the write, system, and irreversible capabilities; the read-tier capabilities are deny or allow only.

A pending approval stores the requested action so the admin can review it. For file and configuration.yaml writes, the before/after diff shown for review and the admin API responses are run through a secret redactor: values on sensitive-looking keys (password, api_key, secret, and similar) and any embedded access keys or URL credentials are replaced with <redacted>, while the structure of the change stays visible. The pending record itself keeps the raw tool arguments while the approval is queued, because an approved action has to re-run with the real content; so for write_file, set_yaml_config and patch_yaml_config the unredacted content can exist in .storage/phoenix_mcp while pending and for up to one hour after resolution. Terminal history is bounded to 500 records and seven days; raw arguments, diffs and results are cleared after one hour.

Personas

You rarely set capabilities one at a time. A persona is a named preset that fills in the entire matrix at once, and choosing one applies the whole set, not just a label. For ordinary personas, adjusting capabilities changes the label to Custom unless the combination matches another preset. Home Companion is different: it retains an enforced, fixed tool boundary until you choose another persona.

Home Companion

Select Home Companion on an access key, then grant READ or WRITE through the normal domain, device and entity permission tree. Inheritance and RED blocks work exactly as for other personas: any RED on the path blocks access; otherwise the most specific non-Grey grant applies. A light-domain READ grant lets it discover and count permitted lights; WRITE also allows control, subject to entity restrictions, MESA and approvals. Supported controls include lights, fans, switches, climate devices, covers, valves, media players, vacuums, humidifiers, input booleans and timer cancellation. Temperature, humidity, illuminance, power, energy and battery sensors, binary sensors, weather, calendars and sun entities are readable only. Search and Registry Read default to Allow, and Physical Control to Confirm. Other capabilities default to Deny. Physical Control governs covers and valves; other household controls use WRITE scope and MESA. You can enable or disable capabilities within this household catalog. Configuration and authoring capabilities cannot add tools outside it. Defaults apply when you select the persona; existing access keys retain their saved capability choices. Pass-through and announce-all are disabled. Choosing another persona ends these additional restrictions.

Home Companion is designed for Agent Chat and Voice; AI Task and external MCP calls remain available. Its colored star marks the different task behavior, and the persona appears before Custom in the picker. Choose a conversation provider and model in Voice settings. Home Companion uses that provider with this access key's own permissions; it does not inherit the Voice access key's scope, and Voice itself need not be enabled. Requests and permitted tool results are sent to that provider. The external client sees only home_request. Its request field accepts a complete natural-language task, with an optional language.

Use natural device names, such as "Alex's office doorway light". The calling assistant is instructed to preserve your wording and restrictions without adding an exact-name requirement. Home Companion uses accessible search results to identify the intended device and asks for clarification if the target remains ambiguous. If you explicitly require an exact name, that restriction still applies.

Home Companion has no conversation memory between calls. Each home_request starts with the supplied request, the permitted tool catalog and Phoenix's task instructions. Tool calls and results are retained while completing that one request. Agent Chat clears its transcript when you submit the next Home Companion request. Earlier requests, earlier answers and the external chat's history are not automatically included. Your chat app may remember them, but must put the relevant context into the new request. Full skill documents and a home inventory are not preloaded.

If a target is ambiguous or a request depends on missing context, such as "turn those lights off", Home Companion asks you to try again with the complete request, including the action, target and restrictions. Phoenix Voice and Agent Chat retain this guidance in their final replies. External clients are instructed to preserve it rather than asking only "Which light?". For example, send "Turn off the kitchen ceiling lights; leave the counter lights on", rather than replying only "the kitchen ones". This applies to the Home Companion tool; it does not describe the history behavior of every Phoenix chat surface.

The fixed internal catalog covers household discovery, state, history, registry reads and native device controls. Capabilities enable or disable access within that catalog. Requests are bounded to four model rounds and eight internal calls; the last model round is reserved for reporting the results, with no further tool calls. Oversized context or catalogs stop the request rather than silently dropping content. Decision Provider routing and tool review do not participate in Home Companion requests.

Conversation style and detail apply to Home Companion replies using the settings for the Phoenix surface you use. External tool calls default to Voice settings. Concise replies state verified power changes directly, such as "Turned off the doorway light", and omit advisory policy explanations. Room summaries use Home Assistant room assignments. Mixed results distinguish confirmed changes from named unavailable or unverified devices. Unverified actions, refusals and required approval still receive guidance. Detail changes the explanation, while execution and state verification remain factual. Home Focus does not expand Home Companion's supported home capabilities. Count answers cover matching Home Assistant entities within your granted scope; groups can be entities too, so this is not a physical bulb count.

Home Companion builds control replies from actual tool receipts and later state readings. A command can be accepted even if the model's final answer is malformed. Phoenix checks the accepted devices' settings when the remaining request budget permits; temperature, position, absolute volume and mute settings have dedicated comparisons. Track changes, relative volume, vacuum actions and timer cancellation can remain accepted without verification; acceptance alone is not proof that physical hardware changed or that every part of your task finished. If the state is not verified, check it in Home Assistant rather than resending the command. Unresolved earlier actions block new requests and require review in Phoenix MCP under Needs attention.

A failed read-only lookup can be refined before valid control. An empty search means no accessible entity matched; it cannot establish whether the name, filters or permissions caused it. Replies ask for a complete new request when clarification is needed. Information limits preserve your requested scope rather than suggesting that all room lights should become one lamp.

Read status, message, execution, verification, next_step, retry_policy, tool_outcomes and review_urls. A completed control report means the command was accepted; check verification for readback. A partial result preserves accepted commands while reporting remaining failures. Approval ends the request before further actions; use the Phoenix panel to review it. Do not automatically retry an outcome_unknown action.

When this persona is bound to Phoenix Voice or Agent Chat, Phoenix sends the current request once and displays its report directly. Free-text AI Task uses the report; structured AI Task formats a completed report to the requested schema without further tools. External chat clients may rewrite the report, so their presentation remains their responsibility. Current state readings come from scoped results; history and statistics summaries still use the language model. Home Companion does not use Decision Provider routing or tool review, regardless of global review settings. Configuration, authoring, filesystem, camera, lock and alarm tools remain unavailable through this persona.

Automation and script write

Manage automations and Manage scripts are elevated-trust capabilities. Enable them only for clients you fully control.

These flags do not consult the permission tree

The write tools edit automations.yaml and scripts.yaml directly. A client with the flag can write an automation referencing any entity in Home Assistant, regardless of what its tree permits. Setting the automation or script domain to RED or YELLOW does not stop them.

  • All or nothing. There is no per-entity scoping for these tools. The flag is on or off.
  • Triggered actions run outside Phoenix MCP. An automation created through Phoenix MCP is run by Home Assistant's own engine, under its own context. Phoenix MCP's permission checks do not apply to what a triggered automation does.
  • Net effect. an access key with a narrow entity scope but this flag enabled could, through a crafted automation, indirectly control entities it cannot reach directly. Treat the flag as broad HA access. See Indirect control risk for the full explanation and an example.
  • Manage blueprints is dual-gated, and its edits reach further than they look. cap_blueprint_write alone is not enough: a blueprint write also requires the capability for the domain it targets, so an access key cannot rewire scripts through a script blueprint while script write is denied. Beyond that, editing a blueprint makes Home Assistant reload every automation or script built from it, while those entities' own configurations do not change at all, so the change leaves no trace in their history. The approval names the entities that will be reloaded; read that list. Deleting is refused by Home Assistant while anything still uses the blueprint.

Pass-through mode

Pass-through access keys skip the three-level permission check and have GREEN access to every entity. They are for trusted tools where maintaining a full tree is impractical.

The tree is a cost control, not only an access control

Because pass-through skips the tree, every context-bearing read (get_states, homeassistant__GetLiveContext, the initial snapshot, an unfiltered search) returns all entities. On a large install that is a recurring token and context cost: every discovery call ships the whole house into the model. A Phoenix MCP scoped access key returns only what you granted and can reduce access key burn significantly.

Pass-through does not bypass:

  • The phoenix_mcp domain blocklist and sensitive-attribute scrubbing
  • Rate limiting
  • Any capability in the write, system, and irreversible group (each must still be enabled)
  • System log read
  • A capability set to confirm, which is gated even under pass-through

All other read-tier capabilities are granted by pass-through. Use pass-through only for tools you fully control.

Pass-through and MESA

Pass-through bypasses Phoenix MCP's per-access-key tree, but it does not bypass MESA, the per-entity safety layer that always runs last (the MESA page covers it in full). When MESA is active, a pass-through access key's writes are still governed by each entity's MESA control_mode. In effect, pass-through hands entity gating to MESA with Phoenix MCP's per-access-key permissions out of the way.

In practice this pattern is niche, for two reasons:

  • The access key and open-read costs above apply in full; every agent sees the entire home.
  • MESA does not provide general read privacy. Camera images have an explicit privacy check; other reads use Phoenix scope and scrubbing. Unprofiled lights are autonomous, locks and alarm panels are prohibited, and every other domain requires confirmation under enforced mode. Advisory mode mostly warns about these control limits. Use the access key tree for least privilege and configure enforced profiles for restrictions that must block.

MESA can be made fail-closed for writes with deployment defaults and enforced mode, but reads stay open and the context cost remains. For most deployments a scoped access key plus MESA is the better combination: the tree scopes what the agent sees (cheap context and read security) and MESA governs write nature on top.
