Operations

Monitor and maintain Phoenix MCP with rate limits, sensors, audit logs, configuration history, and Home Assistant events. See the separate Admin API reference for HTTP automation.

Rate limiting

Each token limits MCP network traffic with a sliding one-minute window.

Default
60 requests per minute, with a burst of 10 per second.
Disable
Set rate_limit_requests to 0 for that token.
Pass-through
Uses the same limits. Edit them on the token detail page after creation.
JSON-RPC batch
Each call spends one request. Phoenix rejects the full batch with HTTP 429 before anything runs when it would exceed the limit.
In-process AI
Agent Chat, Assist, Voice Agent, and AI Task use the steps-before-check-in limit instead. Their tool calls remain audited and counted.

A blocked request returns HTTP 429 and Retry-After. Successful responses include the current limit state.

X-RateLimit-Limit: 60
X-RateLimit-Remaining: 47
X-RateLimit-Reset: 1712345678

If Notify on rate limit is enabled in global settings, Home Assistant raises a persistent notification when a token hits its limit, throttled to once per token per minute.

Telemetry & sensors

Phoenix MCP creates six Home Assistant sensors for each active token. For a token named my_token they are usually named as below. Home Assistant assigns the entity ID when a sensor is first created and resolves any collision by adding a suffix, so copy the real IDs from the device page rather than typing these; tokens created before version 1.0.0 keep whatever IDs they were given then.

EntityReports
sensor.phoenix_mcp_token_my_token_denied_countRequests blocked by permission rules
sensor.phoenix_mcp_token_my_token_expires_inDays until expiry; unknown when the token has no expiry
sensor.phoenix_mcp_token_my_token_last_accessTimestamp of the most recent request
sensor.phoenix_mcp_token_my_token_rate_limit_hitsTimes this token has been rate limited
sensor.phoenix_mcp_token_my_token_request_countTotal requests made with this token
sensor.phoenix_mcp_token_my_token_statusactive in practice: sensors are removed the moment a token is revoked or archived, and expiry archives the token, so the expired / revoked values are only ever visible transiently. Automate on the phoenix_mcp_token_expired / phoenix_mcp_token_revoked events below instead

Sensors are removed automatically when a token is revoked. Renaming a token changes the display name only; the entity IDs are fixed when the sensors are first created and a rename does not move them, so a dashboard card or automation referring to one keeps working. Phoenix MCP's own sensors are blocked from all token access, so an external tool cannot read its telemetry through Phoenix MCP.

Global settings

Tool selection review

Agent Chat, Voice Agent and AI Task each have an independent Tool selection review setting, off by default. Observe only shares bounded task context and the announced tool catalog with the selected Decision Provider and records its recommendation. It does not change which tools run. Advise can ask the conversational model to reconsider one pending batch per turn and generate fresh arguments. Permissions, MESA and approvals still apply.

Active advice requires separate qualification for the selected decision model and request language. No model is currently qualified, so Advise is unavailable. Other models can be observed; errors, low confidence and context or catalog limits leave the ordinary planner in control. Review uses the shared decision timeout and hourly request allowance. It can add latency and model usage; a disagreement is not evidence of a better choice.

Simple direct commands keep their existing fast path. Tool selection review applies only to Phoenix-owned agent loops, not the native Assist bridge or external MCP clients. AI Task uses Home Assistant's configured language for qualification. Aggregate review reasons and decision usage are available in the administrator command-routing preview diagnostics and reset with the integration runtime.

Command routing

In Settings, turn on Handle voice commands directly in Voice Agent or Handle chat commands directly in Agent Chat to handle simple commands before calling your usual AI provider. Both switches default to off. Keep your conversational account configured for other requests. AI Task and the Assist tool-provider bridge are unchanged.

Routing tries Home Assistant's local recognition first. Select an optional account in the Decision Provider card for eligible local misses. With Local only selected, unmatched requests go straight to your usual provider. Saving a new account selects it for enabled routing; it does not turn on either switch. Removing the selected account leaves enabled routing local-only.

Local matches avoid both model calls, so you can benefit from routing without a decision account. JEV or another compatible decision provider can add value when it recognizes a supported command that local recognition missed. If it declines, the usual provider still handles the request, with the decision check adding time and potentially cost. The benefit depends on your commands, models and connection; enabling a decision account does not guarantee faster or cheaper responses.

Automatic routing applies to Phoenix's Voice Agent and Agent Chat, even when their conversational model runs at a remote provider. An external MCP client, such as Claude Desktop or Codex, interprets its own prompts and calls Phoenix tools directly; those MCP calls do not pass through local-intent or JEV routing. The read-only recognize_intent tool can diagnose HA recognition for an external client, but does not execute the command or automatically invoke JEV. AI Task and the Assist tool-provider bridge keep their existing provider behavior.

Language follows the Assist conversation for Voice and the Phoenix panel setting for Chat. Routing accepts the installed Assist language catalog, including the Phoenix UI languages, with regional-tag handling and Simplified/Traditional Chinese aliases. Availability of an individual local sentence depends on HA's rules for that language. Non-English prompts have not been fully tested with JEV or other decision providers; language eligibility is not an accuracy guarantee. Unsupported or unrecognized requests use the usual provider, and the full Chat conversation stays intact.

When upgrading from the experiment, routing and background observation reset to off. Saved accounts and timeouts remain. Enable the new switches when you are ready to use automatic language handling.

Routing statistics

Expand Routing statistics in Voice Agent or Agent Chat to see that surface's totals since the displayed start time. Statistics include requests when direct routing is off. The headline counts requests completed by local intents or the decision provider without a conversational-model call; it is a request percentage, not estimated token savings. Failed, incomplete, cancelled and approval-queued replies are excluded from successful direct completions. A completed write means Phoenix received a successful dispatch result, not independent proof of physical device state.

Sent to conversational provider counts turns that made a model request, including failures. Token totals show actual reported input and output separately for decision and conversational requests, including fallback usage. Missing reports are labelled; partial totals include only reported usage. Failed or cancelled requests may incur unreported usage. Queued approval counts describe the state when the reply ended, not the current approval queue; later approval does not rewrite that historical reply. Previews, model-catalog checks, AI Task and external MCP calls are excluded.

Refresh reads the counters without making a model call. Reset statistics requires confirmation and clears only that card's totals without changing settings. Requests already in progress are excluded from the new period. Aggregates contain no prompts, transcripts, entity IDs or account IDs. They are saved periodically and on normal shutdown, survive restarts, and are cleared by a core data wipe. An abrupt power loss can lose the latest unsaved counts. Voice and Chat statistics remain separate.

Supported commands and permissions

Local recognition handles supported on/off commands, numeric settings and named single-entity primary-state queries using Home Assistant's sentence rules, names and aliases exposed to Assist. Across local and qualified decision routing, numeric coverage includes brightness and light color temperature, media volume, fan speed, cover/valve position and cover tilt, climate and water-heater temperature, humidity, numbers and numeric helpers, and counter values. Each operation must be supported by the target and pass its native bounds, units and precision checks. Cover position means percentage open: 0 closed and 100 open. Arbitrary relative amounts and unit conversions use the usual provider.

Installed HA sentences also support named media pause/resume, next/previous and mute/unmute, plus vacuum start and return-to-base. Each command names one eligible entity and respects its current features and playback state. Vacuum area cleaning and media search/play keep their existing provider/tool paths.

If a local command matches two to five eligible same-name targets, Phoenix can ask you to choose an exact entity. Reply with its number, a supported spoken number, or its exact entity ID; say cancel to stop. The choice expires after two minutes and is used once. Changed names, competing targets, permissions or settings require a new full command. Choosing a target does not approve it: any required approval still appears separately. This works in Voice and Agent Chat with the original conversation intact.

A registered Assist satellite assigned to an area can supply that area when you omit it, such as turn on the lights. An explicit area in your request takes precedence. Phoenix validates HA's satellite/device registration and keeps the same entity permissions. Browser location and typed Chat do not supply a satellite area. Moving or reconfiguring the satellite can invalidate a pending command or approval.

Current-state counts such as how many lights are on? can use local recognition. Qualified JEV can also select a total count, a native-state count or a state breakdown for one domain, optionally limited to a device class and one area. Phoenix computes the answer from fresh authorized states; the model does not calculate it. Replies cover accessible, Assist-exposed, registered entities, excluding aggregate and diagnostic/configuration entities. Unknown and unavailable states stay in the total and are identified in the answer. This scope can differ from a general entity search. Historical summaries, sums, averages, numeric comparisons, exclusions and combined collections use the usual provider. Uncertain decisions also fall back; routing success varies by phrasing and model.

Supported numeric commands can also name an exact entity ID: for example, set light.office to 37 percent brightness, set media_player.office volume to thirty seven percent or set cover.office to 37 percent. Use your actual entity ID. The whole sentence must match an installed HA sentence rule, and the entity must remain exposed to Assist and accessible to your token. Older parsers that cannot verify the original matched text use the usual fallback path. This does not add general entity-ID matching to every local command.

Custom sentence automation matches, unsupported contextual requests, unavailable or unregistered targets and aggregate entities do not run locally. Momentary buttons and scenes may be eligible for an action despite an unknown primary state; unknown state queries still fall back. Area commands bind to explicit targets; approval cannot add new members. Every command still passes Phoenix permissions, MESA, approval and recovery checks. Once dispatched, a denial, pending approval or uncertain result never triggers a second attempt by the conversational provider. Review approvals in Phoenix; reconcile uncertain actions through HA Repairs. Changes to scope, targets, accounts or routing settings invalidate saved command approvals.

After a supported write, Phoenix briefly checks the state reported by HA when current read permissions allow it, accounting for rounding and delayed updates. Its reply distinguishes a matching reported state from a command sent without confirmation. This is not independent proof of the physical device state. Phoenix never resends an action just because verification is missing or delayed.

With qualified JEV, direct routing also covers supported switches and toggles; counter increment/decrement/reset; timer start/pause/cancel/finish; buttons; scene and script actions; cover/valve movement; vacuum and lawn-mower controls; code-free lock actions; media playback, mute, shuffle, repeat and source selection; fan oscillation, direction and presets; and current climate, humidity and water-heater modes. Automation enable/disable follows HA's native behavior: disabling also stops its running actions. Each request names one eligible target. Timer cancel and finish remain distinct because finish fires the finished event.

Select helpers use their current options. Text helpers require one explicitly quoted value; password or patterned fields use the regular provider. Date/time entities and input_datetime accept unambiguous ISO dates and clock times, with local-time validation. Existing named timer helpers accept explicit HH:MM:SS or HA-recognized duration phrases shorter than 24 hours. This does not create Assist timers, reminders or scheduled actions. Relative dates, ambiguous times and unsupported formats fall back.

Sensors, binary sensors, statistics and other readable entities can use a named primary-state query. Qualified JEV can also select a current public attribute, such as brightness, volume, position or temperature. Phoenix reads the selected field through the existing scoped, scrubbed state tool and formats known device units. Primary-state replies use HA translations where available and locale-aware numbers, without changing the original units or precision. Select options and text values stay literal; missing translations fall back safely. Historical statistics, forecasts, calendar/todo contents and editing, structured service arguments, code-protected actions and requests outside the direct operation set use the regular AI agent and existing tools. A primary-state query does not retrieve those richer contents. Coverage does not mean every entity, integration, model and language has been live-tested.

Additional direct candidates include named light colors, current effects and flash; supported native toggles; configured numeric-helper and media-volume steps; select navigation; fan speed steps; vacuum spot cleaning; camera power and motion detection; water-heater away mode; code-free alarm modes; and update skip/clear-skipped. Device features, registered services, current options and permissions determine availability. Code-protected alarm or lock actions and update installation remain outside direct routing.

Live coverage remains incomplete. Attribute reads, sampled multilingual percentages, and fixture-scoped color and numbered-option commands have worked with hosted JEV. Full-catalog numbered-option and timer qualification remains incomplete; narrower fixture success is not evidence of full-home reliability. Color previews have also encountered invalid probability totals. Phoenix rejects malformed or uncertain decisions and uses the usual provider before any action. It does not weaken validation or disable a whole function because one model or prompt fails.

Optional decision account

Add an account using the provider picker: enter its connection details, select Validate to fetch available models, choose a model, then select Done. The new account is selected automatically. Choose Local only to stop using decision providers, or select another saved account row to switch providers. Each saved row shows its default model. Use the pencil to choose another model and Save or Cancel, refresh to reload the catalog, and the trash icon to remove the account after confirmation. Check options explains the fixed decision-routing choices; it does not run the conversational model probe or spend inference credit. TypeSafe / JEV uses its hosted API. System One compatible and Simple-JEV compatible accounts accept a base URL ending in /v1, and an API key only if that server requires authentication. The URL identifies the server; the key authenticates to it, so they can be used together. Setup and model changes validate the selected model against the live catalog; they do not evaluate a command. An unavailable catalog prevents saving a decision model. Decision accounts cannot be used as conversational or AI Task providers.

Numeric commands need no separate switch. HA intent matches keep their recognized value. After a local miss, qualified JEV can choose a supported operation and target only when Phoenix independently verifies the requested absolute value. Decimals are accepted where the native operation supports them; volume, position, fan percentage, humidity and counters require whole values. Values outside the device's bounds or step, ambiguous units and competing amounts fall back. Whole-percentage number words are generated from Unicode rules for the Phoenix UI languages, alongside language-specific percentage markers; this is not universal spoken-number or arbitrary-decimal parsing. Other Assist languages retain only values that their available recognition/evidence paths can verify. Digits in a current option such as HDMI 2 remain part of that option, rather than becoming a numeric setting.

Combined decisions, numeric execution and mixed-history review use TypeSafe's official API with jev-latest or jev-1.13.0, returning revision jev-1.13.0. The eligible language set follows Assist; non-English prompts have not been fully tested with JEV or other decision providers. Other configurations retain supported local and categorical routing, with normal-provider fallback for paths not qualified for that model. The tested Simple-JEV/Qwen3.5-4B setup had numeric and history-review errors. Those are limitations of that revision, not permanent restrictions on future local models. Model validation checks catalog membership, not command accuracy.

Standalone decisions send the command, language, eligible entity IDs, names, aliases and area names, plus operation metadata needed for validation: native units, bounds, precision, current option lists, text-length limits or date/time field types. They do not send the full current state or unrestricted entity attributes. Collection decisions also receive eligible domain, device-class and area selectors, area aliases and allowed native-state filters, without current member states. Typed decisions also receive an independently read candidate value and, for date/time decisions, HA's timezone. Mixed-history Chat review additionally sends the complete supported conversation and a fixed candidate with its service details. Earlier tool results may contain HA state information. Reference review receives history and the eligible light subject. Detected secrets, inaccessible entity IDs, unsupported attachments or excessive content prevent that review. API charges and the provider's data policy apply.

Qualified JEV usually chooses an operation and target in one request, with additional value questions when needed. Larger catalogs can require an initial entity-versus-collection decision and then a request containing the complete relevant catalog. Collection selection can use separate domain, device-class and area choices, which must resolve to one existing scope. Options come from the current target's list; numeric, text and date/time values are independently validated. Every required choice needs a unique highest probability of at least 0.90. This is an admission rule, not measured accuracy or permission. Malformed responses fall back without execution. The official TypeSafe endpoint has bounded tolerance for rounded probabilities; other adapters retain stricter normalization checks. Phoenix does not repair or retry invalid decisions automatically.

Decision targets must be registered, available, exposed to Assist and within the token's scope, with write access and device support where needed. Aggregate entities are excluded. Qualified joint JEV routing, including temporal candidates, supports up to 1,016 candidates using complete groups of 254, each reserving a decline choice. Generic categorical routing supports up to 392 candidates across bounded choice groups, subject to server limits. For larger selections Phoenix checks the selected model catalog for an advertised choice capacity; older servers default to 50 choices per question, including the decline option. Every group sees the complete catalog, and conflicting or uncertain answers fall back. Packed metadata and provider context limits also apply, so these counts are ceilings rather than guarantees. Lossless packing preserves every eligible entity, alias and option. Catalogs are never silently truncated: a catalog that cannot be represented within the applicable limits uses the usual provider. These are decision-request limits, not limits on how many entities Phoenix can manage. Pending approvals bind the exact target, value, account and eligible catalog; changes invalidate the plan.

Connection timing and diagnostics

With an account selected, expand Connection settings to adjust Decision timeout (ms): 250 to 30,000 ms, default 5000 ms. Allow more time for slower connections. Decision questions, numeric source validation and any conversation review share this budget; it does not limit device execution. Local recognition has a separate administrator-configurable budget, default 500 ms. A busy or timed-out evaluation falls back before dispatch, and decision calls are not retried automatically.

Decision requests per hour (0 = unlimited) optionally caps decision API attempts across Voice, Chat, previews, background checks and all decision accounts. The default is unlimited. While enabled, each HTTP attempt reserves one request before sending; failures and uncertain outcomes still count. A reservation is not refunded if cancellation or a later validation check prevents sending. The allowance survives restart and resets at each UTC hour. Changing accounts or resetting routing statistics does not clear it. An exhausted or unavailable allowance skips decision requests and retains ordinary provider fallback. Your conversational provider has separate costs; this is a request limit, not a currency spending cap.

Local-only follow-up routing requires the exact history that Phoenix handled locally, under the same token, routing language and settings. Its verification record expires after 30 minutes, may be evicted under load and is cleared on restart. Mixed-history JEV review can instead consider a complete supported transcript, including supported tool exchanges and retained reasoning. Explicit commands need a fresh review on each such turn. A local match needs one JEV review; an eligible local miss needs two calls within the same decision timeout: candidate selection, then review against the full history. Any proposed value must also pass its operation-specific validation against the latest command. Neither path starts a local-only history chain. Unsupported or oversized history, continuations and one-turn Home-focus overrides use the conversational provider. Nothing is re-executed to verify earlier turns, and history review never replaces permission or approval checks.

Qualified JEV can handle a singular light reference such as turn it off or is it on? after ordinary target selection declines. An earlier explicit command must establish one eligible light. A successfully completed routed reply can retain that subject for further references, bound to the exact transcript, token, language, settings and account. Every reference still receives a fresh review of the full plain-text history and user restrictions. Edited or unsupported history, expired evidence, ambiguous or plural references and relative values use the usual provider. Subject evidence expires after 30 minutes and clears on restart; it never replaces execution or approval checks. Non-English reference prompts remain incompletely tested.

Command previews and observation controls are administrator diagnostics, available through the existing admin API. They are not part of the normal settings card. Previews never execute commands or create approvals. Runtime diagnostics retain aggregate counts, reasons and timing rather than commands or decisions; normal chat history and audit settings still apply.

System-log diagnostics

get_logs and get_phoenix_diagnostics read Home Assistant's in-memory system_log ring through MCP. This is a bounded diagnostic sample, not the Phoenix audit log above and not the raw home-assistant.log file. Home Assistant deduplicates repeated records into buckets and retains only warning-and-above records in this source.

Use the response's source envelope before interpreting an empty result. It distinguishes an available empty ring from an unavailable integration or a degraded upstream shape, and reports capacity, retained buckets, malformed buckets skipped, earliest and latest retained times, and the read timestamp. Continue a clipped query with next_cursor and exactly the same filters. Cursors are snapshot- and filter-bound, but continuation is best-effort because a live bucket can be updated and move while pages are being read.

get_logs requires Log read and excludes Phoenix records. get_phoenix_diagnostics requires both Log read and Diagnostics, includes only Phoenix records, and applies stronger topology, path, identifier, and entity-scope redaction. After a deployment, verify these tools only through the connected Phoenix MCP client after Home Assistant has restarted.

list_integration_log_levels reports effective and stored integration-aware logger settings only for integration domains visible inside the token's resource scope. set_integration_log_level additionally requires the separate, pass-through-exempt Integration log levels capability. Runtime-only timed changes survive Phoenix reloads, restore only while the Phoenix-applied setting remains current, and are discarded rather than reapplied after a full Home Assistant restart. A Phoenix core-data wipe first restores every still-matching timed change.

Logbook diagnostics

get_logbook reads Home Assistant's narrative event history through MCP and returns events chronologically. A home-wide query may cover at most 7 days. Supplying accessible entity IDs, device IDs, or one causal context ID raises that ceiling to 31 days; text search is post-retrieval and does not raise it. Entity and device filters may be combined, while a context filter must stand alone.

Read total and truncated before treating the reply as complete. total is the number left after permission filtering, response redaction, and optional search but before limit; when truncated, reduce the time window rather than looking for a cursor. Home Assistant's underlying logbook command returns one unpaginated database result, so Phoenix deliberately does not offer response-only continuation that would repeat the expensive query and imply a stable snapshot.

Configure advanced token behavior

Advanced token options

Three per-token options sit outside the capability matrix, in the panel's Tool Announcement card on the token detail page (and settable through PATCH).

Always announce all tools
Off by default: a token's tools/list advertises only the tools its capabilities unlock and hides the rest. Turn it on to advertise the full tool list regardless of gating. Calls are still gated, so this changes what a client sees, not what it can do.
Inline approval wait
Off by default. A confirm-gated call returns pending_approval as soon as the approval is queued, so a run of writes reaches the Approvals queue in seconds and you clear them individually or as a batch; the agent asks for the outcome when it needs one. Choosing a duration instead makes the call hold the response open until you decide, which suits a client that never asks, at the cost of the next approval not being created until the previous call stops waiting. This affects external MCP clients only. Agent Chat, the Assist bridge, the voice agent and AI Task ignore it: they queue immediately and wait their own way, so testing the setting in Agent Chat will show no difference.
Limit to Assist-exposed entities
Pass-through tokens only, off by default. A pass-through token normally sees every non-Phoenix entity; enable this to additionally narrow it to the entities exposed to Home Assistant Assist. It is ignored for scoped tokens, which scope by the permission tree, so the toggle is disabled unless pass-through mode is on.

Audit log

Phoenix MCP keeps a circular buffer of requests, viewable in the panel's audit tab or through the admin API. Each entry records a request ID (matching X-Phoenix-Request-ID), timestamp, token ID and name, method, resource path, outcome, and source. After token authentication, pre-dispatch protocol failures are recorded as invalid_request when denied-request logging is enabled; authentication failures have no token audit entry. Every entry produced by one legacy JSON-RPC batch shares the batch's parent HTTP request ID. In the panel, Source shows the caller's IP address for network requests. Requests from Phoenix MCP's own surfaces appear as Agent Chat, Assist Tool Provider, Voice Agent, or AI Task. The admin API continues to expose the underlying value in client_ip.

OutcomeMeaning
allowedThe request succeeded.
deniedBlocked by permission rules, the blocklist, or a RED / NO_ACCESS result. Includes permission-based 404s.
invalid_requestThe request was structurally malformed and rejected before permission checks, for example a template with a syntax error. Also used when an authorised service call carried an argument the target service itself rejected, such as a value outside the range that service accepts: the validator's message is returned so the caller can correct it, which is safe because the call had already passed every permission check and the message describes the caller's own argument. Also used when a permitted action failed for an internal reason, such as a write that could not be saved: those are always accompanied by a full traceback in the Home Assistant log. They are deliberately not recorded as denied, so that outcome stays a reliable list of what your permission rules actually stopped.
not_foundThe entity is genuinely absent from both HA state and the registry. Identical to denied for the caller, but distinguished here so you can tell a missing entity from a permission wall.
not_implementedThe client called an MCP method Phoenix MCP does not support. A protocol gap, not a permission block; does not increment the denied counter.
rate_limitedThe token exceeded its rate limit.
pending_approvalA capability set to Confirm queued the action for admin review instead of running it. Always recorded, even with logging toggles that would otherwise suppress it.

MESA denials are recorded here too, alongside the request that caused them. A companion entry with a method of mesa:enforcement_decision (or mesa:privacy_access, or mesa:lease) names the entity and the rule that stopped it, so you can tell which of a call's targets was the problem. Note the request itself is only logged as denied when the safety layer stopped everything it targeted: a call over several entities where one is blocked and the rest run is an allowed request with a companion denial entry beside it, because that is what happened. Only denials are recorded: the safety layer also reports the accesses it allows, and logging those would push real request history out of the buffer. An entity marked confirm is not a denial either way, so it files no entry; under advisory it runs with a warning, and under enforced it becomes an approval with a record of its own. A preview through dry_run_service never files one, since a predicted block is not a block.

These entries depend on your log level

The safety layer reports its decisions at INFO on the mesa_core.audit logger, and Phoenix MCP deliberately does not raise that level: doing so would override your logging config and put a line in home-assistant.log for every decision. The consequence is that a logger: default above INFO, a common way to quiet the log file, also silences these audit entries. The blocks still happen; only the record of them is lost, and an empty MESA history then looks identical to a safety layer that stopped nothing.

If you have lowered your log level, add this to configuration.yaml to keep the audit trail without turning the rest of the logging back up:

logger:
  default: warning
  logs:
    mesa_core.audit: info

The log is stored in .storage/phoenix_mcp_audit and survives restarts. It is included in HA full backups and in partial backups of .storage. Phoenix MCP flushes on the configured interval and also on HA stop, reload, and unload. Set the interval to "Never" to keep the log in memory only.

Configuration history

Supported configuration writes append best-effort before/after snapshots, viewable in the panel's Changes tab or through the admin API (which also documents the few snapshots that deliberately refuse to restore). The most recent twenty versions per resource are kept, oldest evicted first, so history stays bounded without a sweep. A file or YAML snapshot larger than 100 KB is kept as a metadata-only marker and cannot be restored inline, so a large file cannot bloat storage. Snapshots are stored in .storage/phoenix_mcp_versions and survive restarts; the file is included in HA backups like the rest of .storage. The store is admin-only; restoring a version re-applies it and records a new rollback entry, so the history stays append-only.

Configuration recovery

Open Changes, Configuration recovery after an interrupted or uncertain protected configuration operation. Inspect current state before retrying. A partial replacement helper is retained for review. Mark a record reviewed only after reconciling its effects; this releases its retry block but does not repair the resource. Restore safety copy returns to the captured pre-operation configuration; Restore source applies the selected rollback target. Each restore is a new operation with current safety checks. The panel can restore supported helpers, authored files and YAML, blueprints, Energy preferences, and dashboard registry/layout snapshots. An uncertain write stays blocked until reviewed; a timeout does not establish that nothing changed.

Qualified UI-created Template helpers keep their saved entity ID and custom name when recreated, with a new config-entry ID. Recovery requires the same HA version, a compatible single-entity mapping and an unoccupied saved ID. Unsupported Template mappings, disabled-entity recreation and incomplete legacy snapshots refuse automatic restoration. Person recovery does not retain private user or picture bindings. Generic integrations, device removal and firmware/radio effects have no general automatic inverse. Restoring dashboard registry metadata does not recover a deleted layout; use its separate layout snapshot when available.

Safety records use the separate private .storage/phoenix_mcp_config_recovery store and survive ordinary history rotation and core data wipe. Up to 256 records are retained, with a 1 MiB limit per snapshot. Nothing is evicted automatically: remove resolved records explicitly when no longer needed. Full, unreadable or unwritable storage blocks protected writes. Snapshots that the secret scrubber would alter are refused rather than saved with unusable placeholders. Arbitrary configuration prose can still contain sensitive information. The record list remains admin-only; the MCP restore tool accepts only records owned by its token and checks current authority.

A restart timeout or disconnected client does not mean restart failed. Do not replay it automatically. Reconnect with a fresh client and compare get_config.runtime_identity with the pre-restart identity. A different identity establishes a replaced HA runtime, not proof that a particular request caused it. A Phoenix integration reload alone does not change that identity. Recovery is not a full Home Assistant backup.

MCP and skill routes

POST       /api/phoenix-mcp                                MCP Streamable HTTP endpoint
GET        /api/phoenix-mcp/context                        Token context summary
GET        /api/phoenix-mcp/skill                          Agent skill guide
Authentication
Authorization: Bearer phx_... is required for the MCP and context routes. Tokens in a URL or query parameter are rejected. The skill route is unauthenticated.
Modern MCP headers
MCP-Protocol-Version: 2026-07-28 and Mcp-Method must match the request metadata and JSON-RPC method. Named methods also require Mcp-Name matching the requested tool name, resource URI, or prompt name.
Legacy session header
A 2025-03-26 client sends the Mcp-Session-Id returned by initialize on later requests.
Response framing
Include Accept: text/event-stream to receive the single JSON-RPC response as an SSE event with keepalives. A client asking only for JSON receives application/json.

The MCP endpoint answers a client that advertises text/event-stream with the same single JSON-RPC response delivered as one SSE event, plus a keepalive frame every 15 seconds while the request is still running. Conforming clients for the supported protocol revisions advertise both SSE and JSON; custom JSON-only callers keep the plain response path. That matters behind a reverse proxy: a call held by an inline confirm wait can otherwise sit silent for up to three minutes and get dropped. For modern 2026-07-28 requests, closing the response stream cancels work that has not already committed. Legacy 2025-03-26 requests follow that revision's opposite rule: a disconnect alone is not cancellation.

Phoenix MCP supports two protocol eras on the same endpoint. A modern 2026-07-28 request carries its protocol version and client capabilities in per-request metadata, uses no session, and keeps no resumable SSE event queue. Modern clients may POST only JSON-RPC requests and notifications; a client-sent response object is rejected as an invalid request. A legacy 2025-03-26 client starts with initialize, receives an Mcp-Session-Id, sends notifications/initialized, and includes that session ID on later requests. The server retains at most 256 legacy lifecycle records for up to one hour of inactivity; they are cleared on integration reload. An unknown or expired legacy session returns HTTP 404 so the client can initialize again. Every request in both eras still carries and revalidates its Phoenix bearer token. server/discover reports both implemented revisions, the server identity, and the token-aware primer. A method unavailable in the selected era answers HTTP 404 with JSON-RPC -32601.
